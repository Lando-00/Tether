## Cross-cutting observations

### "NPU execution" is a misnomer for the current setup

All three working models execute on the **Adreno X1 GPU through OpenCL**
(that is what the `*-adreno.dll` files are). The Snapdragon X Elite also
ships a Hexagon NPU, but reaching it requires a different toolchain — most
likely Qualcomm's QNN SDK / AI Engine Direct or the Genie SDK. MLC-LLM's
mainline path on Windows-on-ARM is currently the OpenCL/Adreno path.
Phase 3 of this research surveys the NPU options separately.

### Quantization spread is narrow

We have only `q4f16_0` and `q4f16_1` on disk. The research candidate list
should consciously pull in `q4f32_1`, `q3f16_1`, and `q0f16` builds where
available so we have data points across the precision/RAM trade-off.

### Disk vs RAM is not the same number

These on-disk sizes (~2–4 GB) are **just the weights**. Loaded into the
engine with the configured context window, the KV cache adds substantial
extra RAM. For Qwen3-4B at 40 960 ctx, KV cache alone is on the order of
1.5 GB at fp16; Phi-3.5-mini at the same ctx is similar. The
`scripts/research/estimate_ram.py` script (Phase 4) is what we'll use to
pre-screen candidates honestly against the 9 GB budget.

### Function-calling story is template-dependent

- `qwen3-openai-tools-min` and `qwen2` set `use_function_calling: true`
  and have role templates that already accommodate Tether's
  `<<function_call>>` marker.
- `phi-3` and `gemma3_instruction` both set `use_function_calling: false`.
  They can still be coerced via Tether's system prompt, but expect lower
  reliability.

When evaluating candidates in Phase 4, this column matters more than the
model's "tool-calling capability" on paper — it's specifically about which
**MLC conversation template** got published with the model.
